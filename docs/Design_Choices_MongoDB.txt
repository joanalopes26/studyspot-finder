Design Choices – MongoDB Document Schema (StudySpot Finder)
============================================================

1. Collection Strategy
   The relational schema uses 5 tables (Business, Category, Business_Category,
   Business_Amenities, Review, User).  In MongoDB we consolidate these into
   3 collections — venues, reviews, users — taking advantage of MongoDB's
   flexible document model to reduce joins.

2. Embedding vs. Referencing

   EMBEDDED (denormalised):
   ─ categories      → Array of strings inside the venue document.
     Justification: categories are always read together with the venue, never
     queried as a standalone entity. Storing them as an embedded array avoids
     the many-to-many JOIN table and eliminates the need for $lookup.

   ─ amenities        → Sub-document inside the venue (wifi, noise_level,
                         outlet_mentions).
     Justification: one-to-one relationship; always displayed together with
     the venue.  An embedded object is natural in MongoDB and avoids an extra
     collection or $lookup.

   ─ recent_reviews   → Array of up to 10 recent review summaries embedded in
                         the venue document.
     Justification: enables the "venue detail page" use case with a single
     read.  Bounded to 10 items (maxItems: 10) to prevent document growth.
     Only a snippet (≤200 chars) of the text is stored to keep the venue
     document lightweight.

   REFERENCED (normalised):
   ─ reviews          → Separate collection, referencing venue_id and user_id.
     Justification: reviews are the main data entity (100 000 records).
     Embedding them all inside venues would exceed the 16 MB document limit
     for popular venues and make writes expensive.  A separate collection
     supports paginated listing, aggregation pipelines, and independent
     indexing.

   ─ users            → Separate collection.
     Justification: users are referenced by reviews and may participate in
     multiple venues.  A separate collection avoids duplication and is
     consistent with the relational design.

3. Derived / Computed Fields

   ─ mentions_wifi, mentions_outlets, mentions_pastry  (reviews)
     Boolean flags derived at ingestion time by running regex patterns over
     the review text.  Pre-computing these avoids expensive $regex queries at
     read time and enables efficient indexed filtering.

   ─ outlet_mentions  (venues.amenities)
     Count of reviews that mention power outlets / plugs.  Pre-aggregated at
     ingestion time so the venue listing can sort by outlet availability
     without running an aggregation on every request.

4. Validation Rules
   Strict JSON Schema validation is enforced on all three collections
   (validationLevel: "strict", validationAction: "error") to ensure data
   quality, mirroring the CHECK and NOT NULL constraints used in MySQL.

5. Geospatial Support
   Venue coordinates are stored as GeoJSON Point objects with a 2dsphere
   index, enabling $near and $geoWithin queries for the "find study spots
   near me" use case.  This is equivalent to MySQL's SPATIAL INDEX on the
   POINT column.

6. _id Strategy
   All three collections use the original Yelp IDs as _id (string) instead
   of auto-generated ObjectIds.  This ensures a natural mapping between
   MySQL primary keys and MongoDB document identifiers, simplifying
   cross-database consistency checks.
